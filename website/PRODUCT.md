# Product

## Register

brand

## Users

The primary user is a systems or database developer who already knows SQL. They are evaluating OrnaDB from a Linux workstation, reading source and architecture notes, and deciding whether the programming model is technically coherent enough to follow or contribute to.

## Product Purpose

The website explains OrnaDB as an object-relational database that stores and runs the programs which work with its data. The frontpage must establish the model with real syntax, system boundaries, use cases, and examples. The documentation must give technical readers a short path from the product thesis to the language, invocation, runtime, security, and implementation status.

Success means that a technical reader can answer these questions without marketing interpretation:

- What is OrnaDB?
- How does it differ from a normal SQL database or an application framework?
- What runs on the SERVER and what runs on the CLIENT?
- How can one typed function reach a terminal, JSON consumer, or native UI?
- Which parts exist now, and which parts are design proposals?

## Brand Personality

Mechanical, exact, and candid. The site should feel like a maintained systems manual with a clear point of view. It should create technical confidence without using hype or pretending that unfinished work is available.

## Anti-references

- Generic SaaS landing pages with conversion funnels, testimonial strips, pricing cards, and inflated claims.
- Glossy AI database sites that replace system details with gradients, abstract blobs, and vague promises.
- Beginner SQL tutorials that explain familiar terms to an expert audience.
- Terminal-themed decoration that uses monospace type as a substitute for technical substance.
- Copy that presents a current proposal or roadmap item as a released feature.

## Design Principles

- **Lead with executable syntax.** Show a type, a function, and `orna invoke` before abstract feature claims.
- **Show the boundary.** Make CLIENT, SERVER, runtime, and trust boundaries visible.
- **One function, many surfaces.** Use the presentation path as the main proof of the model.
- **Keep status explicit.** Label implemented work, locked design, current proposals, and open questions.
- **Treat documentation as the product.** Give readers direct routes to examples, architecture, and source instead of a sales funnel.

## Accessibility & Inclusion

Target WCAG 2.2 AA. Keep body text at or above 4.5:1 contrast and important large text at or above 3:1. Support keyboard navigation, visible focus, semantic landmarks, zoom, narrow screens, and reduced motion. Do not use colour as the only status signal. Keep animation restrained and preserve readable content when animation or JavaScript is unavailable.
