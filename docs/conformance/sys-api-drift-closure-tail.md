# SYS API drift closure tail

The generated `api/sys.json` public inventories and schema edges match the frozen `api/sys.json` fixture copied into `orna-conformance-v1/tests/fixtures/reference/`, after normalizing the `source_of_truth` provenance string. That one string differs intentionally: the generated artifact names the local `#[ornasys]` methods as its input, while the frozen artifact names the normative source chapters. `sys_api_drift_closure_tail.rs` pins this relationship.

The reference declares both a human-readable relation `key` and structured `key_fields`, but does not prescribe how their text must be kept synchronized. In this repository, `key` is the `key_fields` paths joined with ` + `. Generation and semantic API loading now reject either representation drifting from the other. This covers valid alternate paths too: a mutation that changes both values still fails the frozen-schema comparison.

The publication source requires effective policy and pending/published state to be visible through `sys.Storage` and runtime maintenance metadata, but it does not specify typed `published_rows` or `published_bytes` fields on `sys.Storage` or `sys.MaintenanceJob`. The frozen API exposes `publication_policy: sys.Value`, pending counters, and `last_publication`; the runtime ledger also carries counters that are not declared public fields. This slice follows the frozen type surface and does not promote those internal counters or add a typed `sys.PublicationPolicy`. Checked-in `.orna` fixtures prove the published fields type-check and the extra runtime fields remain unavailable to portable source.

The final generator-side signature checks now resolve defaults through closed enum variants or singleton value fields, reject defaults whose resolved type differs from the parameter type, and require parameters without defaults to precede defaulted parameters. The semantic API loader already applies the same rules; focused mutation tests pin both sides. The reference lists the current signatures but does not separately define that signature-validation algorithm, so this slice documents the existing loader behavior as the pragmatic rule. Descriptor-backed `Relation<T>` results also retain the semantic relation type used by source annotations. A crate-local `.orna` fixture proves ordinary calls use enum, singleton, boolean, and optional defaults through the published API with explicit relation result annotations.

When a public singleton name prefixes a default path that also resembles an enum variant (for example, `sys.DiffScope.all` with a singleton named `sys.DiffScope`), the semantic loader resolves the longest singleton prefix first. The generator uses the same precedence and rejects the path if the singleton record lacks that field. The reference documents qualified enum variants but leaves this collision rule unspecified; the precedence is pinned as a pragmatic consistency rule.

Removed-name edges now resolve against the same set of live paths accepted by the semantic loader: callable base names, relation and grouped-relation paths, type names, enum names and variants, and singletons. A retired path may not shadow any of those live paths. The reference records replacement names but does not constrain their target kind, so this follows the semantic loader's addressable-path rule. Relation `key_fields` must also be unique; repeated paths cannot add identity information and the semantic loader already rejects them. A crate-local `.orna` fixture proves the nested `sys.DiffEntry.change.area` and `change.target.kind` edges and the `sys.diff` `Relation<sys.DiffEntry>` result remain usable together.

Singleton names and callable base names share a public-value namespace; a singleton cannot shadow a function's overloaded base path. The reference does not define this collision case, so the generator and semantic loader use the same fail-closed rule.

At the published SYS schema boundary, `Relation<T>` arguments must name a declared relation row, a record or record-generic value type, or an in-scope generic row parameter. The frozen schema declares `sys.SourceDocument.maps: Relation<sys.SourceMapEntry>`, so relation inventory alone is too narrow. Applied record rows such as `sys.ValueMetadata<sys.Value>` and `sys.ValueMetadata<T>` are accepted, including function-scoped type parameters; whitespace before a generic argument list is normalized consistently by both schema validators. The reference publishes generic record fields and collection operations, but does not state how descriptor field parameters are substituted when an applied generic row flows through a relation callback. The semantic loader substitutes the declared parameters through nested fields and maps `Relation` members to relation values, following those public descriptors. The crate-local `.orna` fixture proves source-map, concrete and scoped-generic record rows, relation flattening through a generic field, and optional generic value-field substitution.

The reference also does not spell out field projection from a SYS record row inside a relation `map` callback. The published descriptors are used directly: nested `SourceMapEntry.generated.start_byte` projects to `Relation<Int>`, and nullable `SourceMapEntry.original_name` stays `Relation<Str?>`. The fixture proves those relation projections alongside the existing nested `DiffEntry` paths and the `ValueMetadata<T>.protocols` relation-field substitution, using pragmatic descriptor-based substitution for this unspecified callback edge.

The reference is also silent on carrying a projected record as the row type of a following relation callback. The fixture now proves both `SourceMapEntry -> SourceSpan -> Int` across successive `map` operations and a nullable-name `filter` followed by nested field projection. The semantic rule keeps the callback's inferred record descriptor attached to the intermediate `Relation`, so later projections resolve against that descriptor.

The reference does not specify whether a relation callback may capture values from its enclosing function. The fixture captures `SourceDocument.file` inside a `filter` over `SourceDocument.maps`, compares it with each row's nested `generated.file`, and then projects `generated.start_byte`. It also captures the document file in a `flat_map` callback that emits it alongside each row's generated file. These proofs keep the captured outer record and callback row descriptor available for both predicate and collection-producing callbacks.

The reference publishes `ValueMetadata<T>.protocols` and `Protocol.members` as relations but does not spell out flattening each relation-valued record field through a `flat_map` callback. The fixture proves flattening both fields against their respective declared row descriptors: a generic metadata row yields `Relation<Protocol>`, and a protocol row yields `Relation<ProtocolMember>`. The semantic choice is to resolve each callback field from its input descriptor.

The fixture also carries the `Relation<Protocol>` returned by the first generic `flat_map` into a second `flat_map` over `Protocol.members`. The reference does not define this chained callback descriptor rule; this implementation preserves the declared row type across the helper result so the second callback resolves its input field against `sys.Protocol`.

The fixture extends the same rule over three published edges: `Type.parameters -> TypeParameter.bounds -> Protocol.members`, ending at `Relation<ProtocolMember>`. The reference lists these relation fields but does not state whether each successive `flat_map` callback must see the row descriptor produced by the prior callback; the semantic choice is to propagate that descriptor at each step.

The fixture also proves a four-edge chain from `Function.failure_types` through type parameters and protocol bounds to protocol members. The frozen descriptors define each relation edge but are silent on carrying row types across a longer callback pipeline; the semantic loader follows the declared descriptor at every `flat_map` step.

The fixture extends that path through `Function.calls`, so the five-edge proof starts with a function row, enters its called functions, and continues through failure types, generic parameters, bounds, and members. `Function.calls` returns the same declared row type recursively; the loader preserves that descriptor before resolving the rest of the chain.

The fixture also follows `Function.calls` for three successive `flat_map` steps. The reference declares the recursive row field but does not detail repeated callback closure over its returned `Relation<Function>`; each step keeps the `sys.Function` descriptor for the next callback.

The fixture nests two recursive `Function.calls` callbacks and returns a relation containing the root, child, and descendant rows. The reference does not specify capture of rows from enclosing recursive callbacks; the implementation preserves each lexical row descriptor through the nested callbacks, allowing all three `sys.Function` rows to share the emitted relation.

The fixture also takes the helper result from `Function.calls`, filters rows by `Function.inferred_signature`, then follows `calls` again. The reference declares both fields but is silent on retaining the recursive row descriptor across a helper boundary and predicate; the semantic choice is for `filter` to preserve the `sys.Function` row type for the next callback.

The fixture follows recursive `Function.calls` rows into each callee's `effects`, then filters the resulting `Effect` rows by nullable `target`. The frozen descriptors declare these fields but do not specify closure across the recursive `Function` to `Effect` row transition or after a nullable-field predicate; the loader carries the declared `sys.Effect` descriptor through both callbacks.
