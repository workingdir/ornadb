# ADR 0004: Private PostgreSQL Layout Uses Stable Orna Identities

**Status:** Accepted

## Decision

The PostgreSQL kernel uses two protected schemas:

* `_orna_kernel` stores source revisions, semantic catalogue revisions,
  executable artefacts, migrations, and the active revision pointer.
* `_orna_data` stores generated relations for durable Orna object types.

PostgreSQL schemas do not represent logical Orna schemas. PostgreSQL names do
not form part of the public Orna catalogue or language.

Each durable object type has one physical relation. Its name is
`t_<type-id-hex>`. Each field has one physical column named
`f_<field-id-hex>`. Every relation has a hidden `_orna_object_id` column.
Generated names use the lowercase hexadecimal form of the stable 16-byte Orna
identity. Semantic names never enter generated PostgreSQL identifiers, so a
semantic rename does not rename physical storage and a user field named
`object_id` cannot collide with the hidden identity.

All Orna identities are stored as exactly 16 bytes in `bytea` columns with
length constraints. PostgreSQL `uuid` is not the representation of an Orna
identity. `_orna_object_id` is a non-null primary key generated by OrnaDB.

A `REF` field is a 16-byte column with a PostgreSQL foreign key to the target
relation's `_orna_object_id`. Orna `RESTRICT`, `SET NULL`, and `CASCADE`
actions lower to the matching PostgreSQL action. An omitted action lowers to
`NO ACTION`. Relations and columns are created before reference constraints so
mutually referring types can be installed in one apply transaction.

PostgreSQL scalar types are private storage encodings only. They do not expose
PostgreSQL casts, operators, type names, or semantics through the Orna
language.

## Revision contract

An apply bundle is a complete candidate active source snapshot. Bootstrap
creates an empty source bundle, source revision, catalogue revision, and active
revision pointer.

Apply takes an expected base source revision. In one PostgreSQL transaction it:

1. locks the singleton active revision row;
2. rejects a stale expected base before writing;
3. installs supported physical changes;
4. persists the complete ordered source bundle and immutable source revision;
5. persists the semantic catalogue revision and versioned artefacts;
6. advances the consistent active source and catalogue pair.

The first kernel accepts new object relations and changes that do not alter an
existing physical object definition. It rejects unimplemented drops, renames,
field conversions, and data migrations as unsupported migrations. It does not
guess a migration policy.

After restart, OrnaDB reconstructs the exact active source bundle, catalogue,
function revisions, and artefacts from `_orna_kernel` in a repeatable-read,
read-only transaction. Recovery validates identity lengths, revision links,
content hashes, catalogue invariants, and generated physical names. Missing or
inconsistent durable state fails closed.

## Access

The kernel revokes access to both protected schemas from `PUBLIC`. Public
clients cannot address these schemas. The server-side backend shell from ADR
0001 remains the only operator escape hatch.

## Consequences

PostgreSQL supplies durable relations, foreign-key enforcement, transactions,
WAL, MVCC, and its query engine. OrnaDB remains responsible for public syntax,
semantic identities, revision authority, plans, values, and protocol
behaviour.

The logical catalogue schema in `spec/spec/logical_catalog.sql` remains an API
model rather than physical DDL. The private catalogue must additionally retain
empty logical schemas, field uniqueness, ordered source bundles, immutable
source and catalogue revisions, an active revision pointer, and versioned
function artefacts.

## Precedence

This accepted implementation decision resolves the physical choices left open
by `spec/docs/36-storage-transactions.md`. It is constrained by ADR 0001 and
ADR 0003; it does not alter their public-language or source-authority rules.
